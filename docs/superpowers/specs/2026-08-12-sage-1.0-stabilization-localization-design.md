# SAGE 1.0 Stabilization, SSOT Unification, and Localization Design

Status: APPROVED by user on 2026-08-12; baseline amended for merged EH-13-EH-16 on 2026-08-12

Date: 2026-08-12

Readiness target: `1.0.0`; version stamping, tagging, and publication require separate user approval

Released upgrade baseline: `0.9.84` / `v0.9.84`

Frozen implementation baseline: `main@ca9dec0`

Scope: design only; no implementation is authorized by this document

## 1. Purpose

SAGE 1.0 is a stability and usability release. The existing product already contains the
essential governance capabilities. The release therefore prioritizes making those capabilities
safe to maintain, consistent across the repository, usable in Korean and English, and verifiably
upgradeable from the final supported 0.x baseline.

The release has four product goals:

1. Remove or repair stale code, tests, comments, and warnings without changing supported behavior.
2. Make English the canonical language for internal rules, contracts, and procedures while
   keeping Korean as the default language for project-owned code comments and internal docstrings.
3. Keep Korean as the default user-facing language while supporting English through an explicit
   language option and a developer-local preference.
4. Provide a tested, recoverable upgrade path from SAGE `0.9.84` to `1.0.0`.

The governing principle is that localization may change presentation, but must never change a
governance decision, machine contract, generated artifact, audit record, or exit status.

## 2. Release Scope

### 2.1 Included

- Test-runner completeness and warning cleanup.
- Evidence-based removal of dead code, dead tests, and stale comments.
- Korean-default project-owned code comments and internal docstrings, with stale and dead comments
  removed regardless of language.
- English semantic SSOT for framework rules, hook specifications, CORE skill specifications, and
  CORE agent specifications.
- Korean and English CLI help, descriptions, warnings, errors, and block messages.
- Korean and English hook messages.
- Korean and English conversation behavior for CORE skills.
- Korean or English Phase 00-06 prose selected at cycle creation and fixed for the cycle lifetime.
- `--lang {ko,en}` as a global CLI option.
- `interface.language: ko|en` in `sage/project-profile.local.yaml`.
- A bilingual first-run discovery message.
- A dedicated, transactional `sage upgrade` workflow.
- Fresh-install, upgrade, rollback, packaging, runtime, and multi-platform release gates.
- A hard human authorization gate before changing package version sources to `1.0.0`, creating the
  `v1.0.0` tag, or publishing artifacts.

### 2.2 Excluded

- Japanese, Chinese, or other additional locales.
- Operating-system locale auto-detection.
- User-provided translation packs or remote translation services.
- Automatic translation of historical phase documents, audit logs, or Obsidian notes.
- Automatic downgrade from 1.0 to 0.9.
- A guaranteed direct migration from every historical 0.9 release.
- Removal of deprecated public CLI options.
- Repository-wide reformatting, full strict typing, or unrelated refactoring.
- Fully automatic evaluation of natural-language translation quality.
- Any unapproved change to package version sources, Git tags, PyPI, or GitHub Releases.

## 3. Current Baseline and Known Gaps

The design is based on the repository state observed on 2026-08-12.

- The released package and upgrade-fixture baseline is `0.9.84` / `v0.9.84`.
- The implementation baseline is `main@ca9dec0`. It contains the merged, unreleased
  `sage-gate-diagnostics-batch` for EH-13 through EH-16.
- The full hook regression script passes at the implementation baseline.

- The suite emits `ResourceWarning` instances caused by unclosed file reads.
- User-facing Korean strings are distributed across the top-level CLI, command modules,

- Hook decisions are already partly separated through stable `message_key` values, but localized

- The package has clean wheel and sdist checks, but no immutable `0.9.84 -> 1.0.0` upgrade E2E.
- Tag publication currently does not preflight that the Git tag and all package version sources

- Install source-drift failures remain fail-closed and now identify added, removed, and changed

- Adapter processes still consume stdin as part of the hook wire contract; callers that do not
  provide input must close stdin, and the baseline regression test remains enabled.
- The shared machine key `pdca.cycle_binding_visibility` accepts `gated|all`. Missing means
  `gated`, preserving the previous output volume and behavior.
- Opt-in `all` visibility exposes stable `ok_l1` and `ok_l0` message keys with cycle stem and
  origin when a stem exists. It does not invent a cycle when PDCA is disabled.
- Status, exit code, gate decision, audit evidence, and generated artifacts remain unchanged by
  this batch.

These observations are baseline facts to re-check immediately before implementation, because the
repository may change after this design is approved.

## 4. Program Structure

SAGE 1.0 is one release program composed of independently reviewable workstreams:

1. Contract freeze and baseline capture.
2. Test-runner and warning repair.
3. Behavior-preserving code, test, comment, and docstring cleanup.
4. Semantic SSOT language and ownership migration.
5. Localization infrastructure and Korean parity.
6. English catalog and user-facing activation.
7. Upgrade, consumer E2E, and release hardening.

Each workstream must pass its own regression gate before the next one begins. Cleanup, semantic
document migration, and localization must not be combined into one unreviewable change.

### 4.1 Selected approach and rejected alternatives

The selected approach is contract-first, staged migration. It makes failures attributable to one
workstream and lets the team compare every intermediate state with the frozen baseline.

Two alternatives were rejected:

- Localization first: it would add catalogs on top of duplicated and stale output paths, then make
  later cleanup invalidate those keys and translations.
- One large cleanup/localization change: it would shorten the apparent schedule but make semantic,
  packaging, runtime, and translation regressions difficult to isolate or roll back.

The selected approach costs more intermediate validation but has the lowest risk for a 1.0 release
whose primary goals are stability and maintainability.

## 5. Global Invariants

The following invariants apply to every workstream:

1. A language change must not affect a decision, exit code, status, `message_key`, evidence value,
   generated file, audit record, or profile hash.
2. Korean remains the default when no valid language preference exists.
3. Existing projects continue to operate without adding a language setting.
4. Developer-local language data never enters shared governance materialization, manifests,
   decisions, hashes, or audits. Its only intentional committed effect is the selected prose and
   canonical `Document-Language` marker of newly authored Phase 00-06 documents.
5. Machine tokens, commands, paths, keys, IDs, hashes, and enums are not translated.
6. Cleanup and localization are separate changes.
7. No code or test is deleted from static-search evidence alone.
8. Existing user-owned policy, overlays, project-authored assets, plans, evidence, and audit logs
   survive an upgrade.
9. Claude and Codex may use runtime-native files, but their shared semantics remain equivalent.
10. The release does not proceed with an unresolved P0 or P1 issue.
11. Passing implementation and readiness gates does not authorize a `1.0.0` version change,
    tag, push, PyPI publication, or GitHub Release. Those actions require an explicit user approval
    after the implementation and independent review results are reported.

## 6. User-Facing Language Contract

### 6.1 Supported languages

- `ko`: Korean; default.
- `en`: English; optional.

Language codes are exact, lowercase tokens. `EN`, `english`, `ko-KR`, and unsupported codes are
invalid. This keeps configuration and tests deterministic. Additional codes can be added in a
future release without changing the two-code 1.0 contract.

### 6.2 Persistent configuration

The persistent preference belongs only in the Git-ignored local profile:

```yaml
interface:
  language: en
```

The shared `sage/project-profile.yaml` and compiled `sage/project-profile.json` must not contain
this setting. Absence of `interface.language` means `ko`; an upgrade does not add an explicit
`language: ko` entry to an existing local profile.

### 6.3 Resolution order

| Entry path | Resolution order |
|---|---|
| Normal CLI | explicit global `--lang` -> target project's local profile -> `ko` |
| CLI help | explicit global `--lang` -> current/target project's local profile -> `ko` |
| SAGE hook | target project's local profile -> `ko` |
| CORE skill | invocation `--lang` -> target project's local profile -> `ko` |
| New Phase 00-06 cycle | cycle-start skill `--lang` -> target project's local profile -> `ko`; persist once |
| Resumed Phase 00-06 cycle | declared cycle document language; local preference changes are ignored |
| Bare `sage` | bilingual discovery message |
| `sage --version` | language-neutral |

An explicit CLI or ordinary skill `--lang` applies only to that invocation and does not mutate the
local profile. `sage-init` and `sage-init-local` are the exceptions: after user approval, their
language selection is persisted as the developer's local preference.

`sage-plan`, `sage-cycle`, `sage-plan-fast`, and `sage-cycle-fast` are also special in one narrower
sense: when they create a new cycle, their resolved invocation language becomes that cycle's
`document_language`. This does not mutate the local preference. It is persisted as cycle metadata
and controls the human prose authored in every Phase 00-06 document for that cycle.

The public 1.0 configuration surface does not include `SAGE_LANG`. An internal environment value
may transport a resolved language into a child hook process, but it is not a documented user
override and does not add a third public precedence layer.

### 6.4 CLI grammar

The supported global grammar is:

```text
sage [--lang {ko,en}] <command> [command options]
```

Examples:

```bash
sage --lang en --help
sage --lang en doctor
sage --lang ko validate
```

The supported position is before the subcommand. `sage doctor --lang en` is not part of the 1.0
contract. Restricting the location avoids duplicated options in every subparser and prevents
subcommand collisions.

### 6.5 First-run discovery

A bare invocation is no longer treated as an argument error. It prints a short bilingual discovery
message to stdout and exits with `0`:

```text
SAGE 명령을 시작하려면 도움말을 확인하세요.
한국어 도움말: sage --help

To get started with SAGE, open the help page.
English help: sage --lang en --help
```

`sage --help` is Korean and ends with the English discovery command. `sage --lang en --help` is
English and ends with the Korean discovery command. Ordinary operation uses one selected language;
only discovery and unsupported-language errors are bilingual.

### 6.6 Invalid settings

An unsupported explicit language is an input error with exit code `2` and a concise bilingual
message. A malformed local value falls back to Korean, emits a bilingual diagnostic, and is a
configuration failure in `sage validate`. A malformed language preference must not alter or stop
the underlying hook governance decision.

## 7. Language Resolution Architecture

### 7.1 CLI flow

The CLI must determine language before constructing the full `argparse` tree:

```text
argv
  -> non-failing bootstrap scan for --lang and target-root hints
  -> local-profile language lookup when needed
  -> LanguageContext
  -> localized full parser construction
  -> final parse
  -> command execution
```

`LanguageContext` has exactly the data needed by presentation code:

```text
language: ko | en
source: cli | local_profile | default
fallback_used: boolean
```

The bootstrap scan must not emit final parser errors. It discovers only the explicit language and
the likely project root or destination. The localized full parser owns validation and error output.

Commands with `--root`, `--dest`, or `--profile` resolve their target project through command
metadata in the command registry. Individual command modules must not independently invent
language precedence.

### 7.2 Local profile validation

`schema/profile.local.schema.json` and `sage/profile_layers.py` add only:

```text
interface.language in {ko, en}
```

Unknown `interface` keys fail validation. The effective governance profile may expose the resolved
interface value to presentation consumers in memory, but shared materialization remains unchanged.

### 7.3 Hook flow

Hook governance continues to read the compiled shared profile. Output language is read separately:

```text
hook event
  -> project-root resolution
  -> shared project-profile.json -> governance decision
  -> local interface.language    -> presentation only
  -> message_key + arguments
  -> locale render
  -> Claude or Codex runtime formatting
```

The hook decision core must not import locale modules. The hook entrypoint or runtime layer reads
only the validated local language scalar and must not merge the local profile into
`project-profile.json`.

### 7.4 CORE skill flow

The skill instruction itself is canonical English. At invocation time the skill applies the same
resolution rule and uses the chosen language for questions, progress explanations, warnings,
blocks, and summaries. Commands, paths, schema fields, parser markers, statuses, and audit bindings
remain unchanged.

`$sage-init --lang en` conducts the bootstrap in English and persists `interface.language: en`.
`$sage-review --lang en` uses English for that review only.

These `$sage-* --lang` forms are conversational skill invocation arguments, not subcommands of the
`sage` executable. The CLI and skill syntaxes share the same language codes and precedence meaning
but are parsed by different runtimes.

### 7.5 Phase document language lifecycle

For a new standard or Fast cycle, the planning skill resolves the document language exactly once:

```text
explicit cycle-start skill --lang
  -> project-profile.local.yaml interface.language
  -> ko
```

The first Phase 00 document records exactly one machine-readable declaration outside code fences:

```text
Document-Language: ko
```

Every later Phase 01-06 document with the same `Cycle-Stem` records the same declaration. Human
prose, including headings, requirements, design explanation, implementation notes, analysis,
review narrative, and final report prose, is authored in that language. Machine vocabulary such as
`Cycle-Stem`, `Document-Language`, `Risk Level`, acceptance IDs, verdicts, paths, commands, hashes,
schema keys, and enum values remains canonical and untranslated.

After Phase 00 exists, its `Document-Language` is the durable source of truth. The Git-ignored
`.sage/cycle.json` mirrors it as `document_language` for runtime resume and cross-host handoff. A
later local-profile change or a conflicting skill `--lang` cannot change an active cycle; the skill
must continue in the declared language or stop with a localized conflict message. It must never
silently mix languages within one cycle.

`sage cycle set` validates the exact Phase 00 declaration and copies it into the declaration file.
`sage cycle set --create` resolves the current language context, writes the localized Phase 00
skeleton with the canonical marker, and persists the same value atomically. Context snapshots,
restore briefings, `/sage-team`, `/sage-review`, and Phase 06 all transport and revalidate this
value. A mismatch among same-stem phase documents, Phase 00, restored context, and cycle state is a
hard pre-write/review/completion block.

Cycles created before this contract are not bulk-edited. A legacy cycle without
`Document-Language` remains undeclared. SAGE does not reinterpret it as Korean: the cycle state
reads back `document_language=None`, `.sage/cycle.json` cross-checks Phase 00 rather than declaring
in its place, and a failure to read either one is a block, not an absence. Existing historical
documents are not rewritten. On resume, the skill follows the language already used by the cycle
and introduces the marker only through the documented revision/resume workflow. New cycles may
never omit the marker.

Structural gates can prove marker consistency, and the English path can reject uncategorized Korean
leakage. The Korean path also requires non-empty Korean prose in translatable sections so an
accidentally all-English document fails smoke validation; technical English tokens remain allowed.
These checks cannot fully prove natural-language quality. Korean authoring quality and semantic
translation quality therefore remain subject to Phase 04 and independent Phase 05 review.

## 8. Localization Architecture

### 8.1 Decision and presentation separation

All localized output follows this model:

```text
input
  -> language-neutral decision/result
  -> key + named arguments + stable status/exit code
  -> selected-locale rendering
  -> output-channel/runtime formatting
```

A representative hook result is:

```json
{
  "status": "block",
  "exit_code": 2,
  "message_key": "block_phase_incomplete",
  "message_args": {
    "missing_phases": ["04", "05"]
  }
}
```

The two languages may produce different prose, but the structured result above is identical.

### 8.2 Catalog format

SAGE 1.0 uses packaged Python dictionaries rather than adding a gettext or external parsing
dependency:

```text
sage/i18n/
  __init__.py
  ko.py
  en.py
  validation.py
```

Catalogs are divided by domain instead of being one unbounded dictionary:

- CLI common and parser messages.
- CLI command-specific messages.
- Hook gate messages.
- Hook profile and runtime diagnostics.

Hook runtime copies must remain self-contained when executed from an installed consumer project.
Their locale modules therefore live inside `scripts/sage_harness/hooks/runtime/` and cannot assume
that the main `sage` package is importable.

The concrete ownership is:

- CLI catalogs: `sage/i18n/ko.py` and `sage/i18n/en.py`.
- Hook catalogs: `scripts/sage_harness/hooks/runtime/i18n/ko.py` and
  `scripts/sage_harness/hooks/runtime/i18n/en.py`.
- Aggregate build-time catalog oracle: `sage/i18n/validation.py`. It may load packaged hook
  resources through `sage._resources`, but hook runtime code never imports this module.

### 8.3 Key policy

New CLI keys use semantic namespaces such as:

```text
cli.install.completed
cli.validate.profile_invalid
cli.doctor.peer_unavailable
cli.parser.unsupported_language
```

Existing hook `message_key` values are compatibility contracts and retain their current names,
including values such as `block_phase_incomplete` and `warn_l2_no_plan`.

Keys describe meaning, not sentence wording. CLI and hook keys are not shared merely because two
current sentences look alike.

The two catalog domains are intentionally disjoint. Existing hook keys such as `ok_l1` and
`ok_l0` exist only in the hook catalog; CLI keys use the `cli.` namespace. The aggregate catalog
oracle owns four checks: Korean/English parity inside the CLI domain, Korean/English parity inside
the hook domain, zero key collisions between domains, and coverage of every statically referenced
hook key. There is no requirement for CLI and hook catalogs to have the same key set.

### 8.4 Complete-message translation

Catalog entries are complete messages. Translated fragments are not concatenated because word
order and plural forms differ. Named placeholders carry paths, counts, IDs, and external evidence.

Korean and English must have identical placeholder sets. Catalog validation fails on missing keys,
additional keys, placeholder mismatch, invalid format syntax, or incomplete plural variants.

### 8.5 Runtime formatting

Locale and runtime are separate dimensions:

- Locale controls explanation, reason, warning, block, and recovery guidance.
- Runtime controls `/sage-review` versus `$sage-review`, emoji, separators, channels, JSON wrappers,
  and host-specific line formatting.

The pipeline is `semantic message -> locale render -> runtime format`. Locale/runtime combination
branches must not proliferate through the decision core.

### 8.6 Missing translation behavior

- Missing selected-locale key: fall back to Korean and emit a non-sensitive diagnostic.
- Missing Korean key: emit a language-neutral `[SAGE] message_key=<key>` message.
- Formatting failure: report the key and missing placeholder name, not the complete parameter map.
- Never silently drop an unknown key.
- Preserve the original governance decision and exit code in all fallback cases.

English-mode Korean leakage is a release-test failure even though the runtime fallback remains
defensive in production.

### 8.7 Reasons and external evidence

Localized reasons use `reason_key` and `reason_args`. Git, Python, OS, or external-tool errors remain
verbatim evidence and are wrapped in a localized explanation. Existing public `reason` fields are
retained at the IO boundary when compatibility requires them.

### 8.8 Output channels

Localization does not independently move output between stdout and stderr or change established
exit codes. The only intentional top-level change is bare `sage`, which becomes a successful
discovery action.

| Output | Channel | Exit status |
|---|---|---|
| Help | stdout | `0` |
| Version | stdout | `0` |
| Successful command result | existing stdout contract | `0` |
| Input error | stderr | `2` |
| Runtime failure | existing command contract | existing value |
| Bare `sage` discovery | stdout | `0` |

### 8.9 Machine-readable output

JSON field names, enums, statuses, hashes, paths, and IDs are never translated. A human-readable
`message` or host-required `reason` value may be localized. Automation must use stable fields such
as `status` and `message_key`, not compare prose.

New structured fields are additive and require compatibility review. Host hook schemas must not be
extended unless the host contract permits it.

## 9. Code, Test, Comment, and Docstring Cleanup

### 9.1 No behavior change

Cleanup preserves CLI commands, options, channels, exit codes, hook decisions, `message_key`
values, JSON contracts, generated files, installed assets, and the Korean baseline. Localization is
not implemented in this workstream.

### 9.2 Work categories

| Category | Work | Behavior change allowed |
|---|---|---|
| Test execution repair | Wire missing tests and verify inventory | No |
| Warning repair | Close files and improve isolation | No |
| Comment/docstring cleanup | English unification and stale-text removal | No |
| D0 cleanup | Unused imports, local variables, obvious duplication | No |
| Structural deletion | Helpers, modules, templates, compatibility paths | Separate approval |

### 9.3 Test-runner contract

The set of `test_*.py` files must equal the set run by `run-all.sh` plus an explicit,
machine-readable exclusion list. Exclusion entries include the file and a concrete reason.

The existing runner is retained initially. The two currently omitted tests are wired before any
test cleanup. A later switch to automatic discovery requires a separate proof that ordering,
working-directory, and environment assumptions have been removed.

### 9.4 Test classification

Every candidate test is classified as active, unwired, duplicate, retired-contract, or test
support code. A duplicate test can be deleted only when target behavior, input, path, assertions,
and detected regression class are all equivalent. A newly failing test is not automatically stale.

### 9.5 Dead-code evidence

Deletion requires evidence from all applicable categories:

1. Static references: imports, calls, exports, CLI registration, string references.
2. Dynamic and packaging references: dynamic imports, subprocess invocation, filename dispatch,
   globs, bundled resources, templates, manifests, installed assets, and generated inputs.
3. External contracts: console entrypoints, public imports, commands, options, hook IDs,
   `message_key`, skill/agent names, schemas, and documented paths.

Coverage absence is only supporting evidence. Uncertain dynamic assets remain in place.

Deletion risk classes are:

- D0: local unused import/variable; removable with focused tests.
- D1: private helper or duplicate internal path; removable with focused and full tests.
- D2: module, template, hook helper; requires recorded evidence and packaging/runtime E2E.
- D3: public CLI/import/schema/message key; retained in 1.0 and deprecated first if necessary.
- D4: unresolved dynamic use; retained and documented for later investigation.

### 9.6 Comment policy

Natural-language explanations in project-owned code comments, shell comments, YAML developer
comments, test comments, and internal docstrings use Korean by default. Exact external literals,
machine tokens, generated files, and vendored assets are not forced into a language. Code comments
and internal docstrings are excluded from the English source-language gate.

Comments explain non-obvious reasons, contracts, safety decisions, or runtime differences. They do
not repeat code, preserve removed behavior, act as an untracked changelog, contain commented-out
code, or retain unactionable TODOs. TODO/FIXME entries are resolved, linked to a tracked item,
rewritten as a durable constraint, or removed.

Docstrings are required for public interfaces and complex decision, profile, materialization,
runtime adapter, state, exit-code, and side-effect contracts. Small self-explanatory private
helpers do not require ceremonial docstrings.

### 9.7 Static analysis

CI initially enables only high-confidence blocking rules, including syntax errors, undefined
names, unused imports/local variables, duplicate dictionary keys, and invalid format strings.
Dead-function and complexity tools produce review reports, not automatic deletion or immediate CI
failure. Full strict typing and repository-wide formatting are outside 1.0.

### 9.8 Warning policy

Existing `ResourceWarning` instances are inventoried and repaired before warning enforcement.
After cleanup, `ResourceWarning` is promoted to a regression gate. Warning suppression is not a
valid fix unless the warning is proven external and documented.

### 9.9 Cleanup sequence

1. Wire omitted tests and add runner-completeness validation.
2. Repair `ResourceWarning` and isolation defects.
3. Remove or repair stale comments/docstrings in bounded module groups and verify the Korean-default
   policy on changed explanatory prose.
4. Remove D0 candidates.
5. Review and remove proven D1 candidates.
6. Handle each D2 candidate independently.

Each unit runs focused tests, the complete hook suite, CLI contract checks, schema and manifest
validation, wheel smoke, and normalized before/after behavior comparison.

## 10. Semantic SSOT Language and Ownership

### 10.1 Language by document role

| Document role | Canonical language | Policy |
|---|---|---|
| Rules, contracts, procedures | English | One canonical source |
| Code comments and internal docstrings | Korean by default | Exact literals, machine tokens, generated and vendored assets are exempt from language forcing |
| CORE skill and agent instructions | English | User response follows selected locale |
| Hook decision specifications | English | User messages use locale catalogs |
| General user documentation | Korean and English | Korean source plus reviewed English mirror |
| Historical plans/reviews/reports | Original language | No bulk translation |
| Phase 00-06 planning documents | `Document-Language` (`ko` or `en`) | One language fixed at cycle creation |

### 10.2 Canonical owners

| Concern | Canonical owner |
|---|---|
| Global PDCA, risk, and safety | `AGENT_GUIDE.md` |
| Localization behavior | source `templates/core/framework/docs/agent/language-policy.md`; installed render `docs/agent/language-policy.md` |
| Review details | `docs/agent/review-protocol.md` |
| Phase document structure | `docs/agent/pdca-templates.md` |
| One hook decision contract | `docs/sage_harness/hooks/<id>.md` |
| One CORE skill procedure | `templates/core/skills/<id>.md` |
| One CORE agent role | `templates/core/agents/<id>.md` |
| CLI usage | `docs/cli-reference*.md` |
| Profile usage | `docs/profile-reference*.md` |

Non-owning documents link to or summarize the owner; they do not redefine the rule.

`language-policy.md` is a managed CORE framework document, not a repository-only user document.
Its source is packaged under `templates/core/framework/docs/agent/` and `sage install` copies it to
the consumer's `docs/agent/`. The installed file receives a shared framework-document receipt in
`manifest.core_renders` under the stable key
`shared/framework-doc/docs/agent/language-policy`; install and validate compare its canonical base
hash. Because it is in the templates tree, it is also included automatically in the aggregate
source identity and EH-13 logical-path drift inventory. Wheel, sdist, install, force-upgrade, and
upgrade fixtures must prove the file is present and current.

### 10.3 Semantic specifications

The following become English semantic SSOT:

- `templates/core/framework/AGENT_GUIDE.md`.
- `templates/core/framework/docs/agent/*.md`.
- `templates/core/framework/verification-protocol.md`.
- `docs/sage_harness/hooks/*.md`.
- `templates/core/agents/*.md`.
- `templates/core/skills/*.md`.

`sage-init` and `sage-init-local` receive missing neutral specifications so all 13 CORE skills have
one semantic specification and one reviewed runtime render source.

### 10.4 Runtime-native renders

Claude and Codex discovery formats and capabilities differ. SAGE therefore retains runtime-native
files derived from shared semantics:

```text
English semantic specification
  -> reviewed Claude runtime render
  -> reviewed Codex runtime render or host-appropriate installed copy
```

Semantic specifications own the common procedure, invariants, errors, outputs, and localization
rules. Runtime renders own frontmatter, discovery paths, host tool invocation, model/effort syntax,
and explicitly allowed runtime deltas.

Natural-language render bodies are not fully machine-generated in 1.0. Each render records its
canonical source and normalized source hash. A changed source makes the render stale until it is
reviewed, synchronized, and restamped. Hash equality proves review acknowledgment, not semantic
translation quality.

### 10.5 Allowed Korean in English SSOT

Korean is allowed only as categorized data:

- `localized-data`: user trigger or catalog text.
- `compatibility-fixture`: test input or historical compatibility case.
- `external-literal`: externally defined proper name or exact string.

Uncategorized Korean explanatory prose in an English SSOT file fails documentation validation.

### 10.6 User documentation

README, quickstart, CLI reference, profile reference, troubleshooting, architecture, and artifact
ownership documents remain bilingual. The current contract remains:

- Korean is the authoring source.
- English is a reviewed mirror.
- The English mirror records the normalized Korean source hash.
- A changed Korean source makes the English mirror stale until human review.

This source direction is intentionally not reversed during the internal SSOT migration. Hash
agreement does not claim semantic translation quality.

### 10.7 Historical evidence

Completed phase documents, review evidence, and reports are not bulk-translated because doing so
would invalidate hashes, approval bindings, and historical evidence. If an active legacy semantic
document requires substantive modification, its full owning document is migrated to English as
part of that scoped change.

Consumer-project plan and report prose may follow the selected user language, but parser-visible
headings, keys, IDs, statuses, hashes, and binding markers remain canonical tokens.

### 10.8 SSOT migration sequence

1. Inventory role, owner, language, source, and derived outputs for every governed document.
2. Lock the glossary and non-translatable token list.
3. Migrate global framework contracts.
4. Migrate seven hook specifications.
5. Normalize six CORE agent specifications.
6. Complete and normalize 13 CORE skill specifications.
7. Synchronize and hash runtime renders.
8. Synchronize bilingual user documentation.
9. Validate links, hashes, conformance, installation, and packaging.

## 12. Output Inventory and Migration

Before localization implementation, every user-visible output is registered with:

- Stable inventory ID.
- File and function.
- Current text.
- stdout/stderr/channel location.
- Current exit code.
- Text or JSON format.
- Known machine consumer.
- Dynamic placeholders.
- Localization classification.
- Existing or required tests.

The inventory covers `sage/cli.py`, every `sage/commands/*.py` module,
`sage/hook_entry.py`, hook runtime IO and message modules, core decision reasons, install/doctor/
validate reports, and CORE skill interaction rules.

The post-approval EH-13-EH-16 baseline adds explicit inventory requirements:

- Localize the human labels and explanation in install source-drift diagnostics, while preserving
  logical resource paths, counts, hashes, exception types, and fail-closed behavior.
- Register `ok_l1` and `ok_l0` as stable hook keys with Korean and English catalog parity. Preserve
  cycle stem and origin values verbatim.
- Localize validation and documentation prose for `pdca.cycle_binding_visibility`, but never
  translate the schema key or the `gated|all` tokens.
- Preserve the default `gated` behavior and the no-stem/no-message behavior in both languages.

Migration proceeds command by command. Each command first reproduces its current Korean behavior
through the Korean catalog, then receives English entries. A hard-coded user-facing string check
prevents regression after migration, with explicit allowlists for fixtures and external literals.

## 13. Upgrade Design

### 13.1 Supported upgrade floor

The guaranteed direct path is `0.9.84 -> 1.0.0`. Earlier 0.9 projects must first converge on
`0.9.84`, validate, and then upgrade to 1.0. This avoids claiming untested compatibility with every
historical installation shape.

Supported shapes include Claude, Codex global skills, Codex project-local skills, dual-host
receipts, local-profile absence, and valid existing local profiles.

### 13.2 Dedicated command

SAGE 1.0 introduces:

```bash
sage upgrade --check
sage upgrade --apply
```

`--check` is read-only and reports current/runtime/installed/generated versions, host and skill
scope, managed drift, schema state, overlays, project-authored assets, planned migrations, changed
files, and blockers.

`--apply` performs a transactional migration:

1. Preflight and input hash capture.
2. Backup.
3. Managed CORE asset update.
4. Required schema migration.
5. Precise `sage.required_version` update.
6. Manifest and receipt refresh.
7. Shared profile recompilation.
8. Hook registration regeneration.
9. Overlay rematerialization.
10. Full validation.
11. Commit-or-rollback result report.

The upgrade command remains callable during a version mismatch; otherwise the mismatch would
prevent its own remediation.

### 13.3 Install versus upgrade

`sage install --force` repairs or re-installs managed assets for the current required version.
`sage upgrade` moves a project between versions and updates the exact version contract. Version
mismatch diagnostics point to `sage upgrade --check`, while same-version stale or missing assets
continue to use `sage install --force`.

### 13.4 Preservation

Upgrade preserves project risk, components, paths, PDCA policy, team/model configuration, the local
profile, project-authored assets, overlays, phase documents, review/acceptance evidence, `.sage`
audit logs, vault data, project code, and project-owned verification scripts.

The shared YAML is not reserialized or replaced. Only the exact
`sage.required_version: 0.9.84` scalar is migrated to `1.0.0`, preserving comments, order, and
project policy.

### 13.5 Drift and force

A user-modified managed CORE file blocks normal upgrade. The report directs the user to move the
customization into an eligible overlay or project-authored asset, back it up, or explicitly discard
it. `sage upgrade --apply --force` authorizes replacement only of SAGE-owned managed drift; it does
not authorize replacement of local profiles, project policy, overlays, project-authored assets,
plans, or code.

### 13.6 Atomicity and recovery

Preflight rejects malformed profiles/manifests, unsafe links, path escape, unknown managed drift,
unresolved host/scope, missing resources, unsupported source versions, insufficient permission,
and concurrent input changes.

Rollback covers managed framework files, CORE renders, hook runtime, manifest, exact required
version, compiled profile, host registrations, and Codex global skills. User-owned data is not an
upgrade write target.

A local, Git-ignored report may be stored under `.sage/upgrades/<run-id>.json`; it records version
axes, migration IDs, managed asset IDs, validation result, and rollback state without private paths
or local profile values.

### 13.7 Downgrade

Automatic downgrade is unsupported. Recovery uses the pre-upgrade backup or a documented manual
process: remove 1.0-only local keys, restore `required_version`, install `0.9.84`, restore that
version's managed assets, regenerate, and validate.

## 14. Backward Compatibility

SAGE 1.0 retains:

- Existing command and option names.
- Existing command exit-code contracts, except bare `sage`.
- Hook IDs, statuses, and `message_key` values.
- JSON keys and enum tokens.
- Existing profile keys.
- CORE installation paths and host semantics.
- Project-authored assets and overlays.
- Missing-local-profile behavior, now explicitly interpreted as Korean.
- Deprecated public options throughout the 1.0 line.

The intentional compatibility change is bare `sage`: exit `2` becomes exit `0` with bilingual
discovery. Automation that used bare `sage` as an installation probe must use `sage --version`.
This change is prominent in release notes.

Exact human-readable prose is not a stable machine contract. Tests and consumers must prefer
structured keys and statuses. Selected UX snapshots remain to protect intended presentation.

## 15. Verification Strategy

### 15.1 Contract freeze

Before behavior-preserving work begins, capture normalized baselines for:

- CLI command tree, help, channels, and exit codes.
- Hook status, exit code, key, evidence, and runtime wrappers.
- Generated file sets and hashes.
- Shared profile compilation.
- Installation trees and manifests.
- Claude and Codex runtime behavior.

Volatile timestamps, UUIDs, temporary paths, and machine-specific paths are normalized before
comparison.

### 15.2 Localization tests

- Korean and English key sets are identical.
- Placeholder and plural variants are identical.
- Referenced keys exist; unused keys are reported.
- English CLI/help/hook output has no uncategorized Korean leakage.
- CORE skills contain no fixed Korean-response instruction.
- New standard and Fast cycles resolve document language from explicit cycle-start `--lang`, local
  preference, then `ko`, and record one matching `Document-Language` in every Phase 00-06 document.
- Active-cycle tests change/remove/corrupt the local preference and prove that the Phase 00
  declaration still wins across Claude/Codex resume and context restore.
- Missing, duplicate, invalid, or conflicting document-language markers block phase writes,
  independent review, and completion without mutating phase evidence.
- Legacy version-1/no-marker cycles resolve to Korean without rewriting historical evidence; the
  first governed new write records the canonical marker.
- Every subcommand and nested action has Korean and English help coverage.
- Identical Korean/English invocations produce equal decisions, statuses, keys, JSON structure,
  generated files, audits, and profile hashes.
- OS locale does not choose product language.
- EH-13 drift diagnostics produce equivalent added/removed/changed path sets in both languages,
  without changing the aggregate source hash.
- `pdca.cycle_binding_visibility` missing and `gated` preserve the baseline output; `all` renders
  localized `ok_l1`/`ok_l0` text with identical keys, cycle stem, origin, status, and exit code.
- PDCA-disabled or otherwise stemless decisions do not gain a fabricated binding message in either
  language.

Required top-level cases include:

```bash
sage
sage --help
sage --lang ko --help
sage --lang en --help
sage --lang fr --help
sage --lang en doctor
sage --lang en validate
sage install --help
sage --lang en install --help
```

### 15.3 Fresh consumer tests

Fresh-install matrices cover:

- Claude project-local runtime assets.
- Codex project-local skills.
- Codex global skills.
- Korean default.
- Explicit Korean and English local preferences.
- Invalid local preference fallback.
- Explicit per-invocation override.
- Real PASS and BLOCK hook paths.

### 15.4 Immutable upgrade fixtures

Actual released `0.9.84` output is captured as immutable consumer fixtures rather than manually
approximated. The expected 1.0 destination includes the contracts already merged at
`main@ca9dec0`; the unreleased merge does not replace `v0.9.84` as the migration source fixture.
Fixtures include representative profiles, manifests, Claude and Codex installation surfaces,
generated hooks, render receipts, an overlay, a project-authored asset, and audit samples.

Upgrade E2E verifies check, apply, validation, actual hook execution, policy preservation, local
profile preservation, overlay/project-asset preservation, version convergence, both locales,
idempotent second execution, and injected-failure rollback.

### 15.5 Packaging and platforms

CI retains Python 3.10, 3.11, and 3.12. Required release checks include full test inventory,
warning-free execution, static blocking rules, documentation validation, catalog parity, locale
snapshots, decision equivalence, golden consumer E2E, upgrade E2E, schemas, manifests, sdist
resource guard, wheel-only smoke, and clean pipx-style smoke.

Linux, macOS, and Windows smoke verify package installation, both help languages, local preference,
validation, native `sage-hook`, and safe UTF-8/non-UTF-8 output behavior.

## 16. Release Engineering

### 16.0 User authorization boundary

The implementation cycle may make the codebase ready for 1.0 and may exercise a parameterized or
isolated candidate build. It must not change the repository's package version sources to `1.0.0`,
create or push `v1.0.0`, publish to PyPI, or create a GitHub Release.

After independent review, the cycle reports either `NOT READY` or
`READY_FOR_USER_RELEASE_DECISION`. Only an explicit user approval issued after that report opens a
separate release action that may stamp versions and run the final immutable `1.0.0` package E2E.
Silence, approval of this design, approval of implementation, or a passing Phase 05 review is not
release authorization.

### 16.1 Version consistency

Before tagging, package-related version sources must agree:

- `pyproject.toml`.
- `sage/__init__.py`.
- `templates/project-profile.yaml`.
- Package-related fields in `docs/sage_harness/.manifest.json`.
- Built wheel and sdist metadata.
- Git tag `v1.0.0`.

`template_version`, adapter contract versions, and manifest schema versions remain independent
where they represent different contracts. Their ownership and semantics must be documented rather
than forced to equal the package version. Existing inconsistent manifest sample or template values
are normalized before release.

### 16.2 Publish guard

The release pipeline becomes:

```text
tag
  -> tag/package version match
  -> full release checks
  -> sdist and wheel build
  -> metadata validation
  -> clean-install smoke
  -> PyPI publication
  -> GitHub Release
```

Publication blocks on version mismatch, an already published version, resource omissions, catalog
incompleteness, stale canonical/render or bilingual-document hashes, failed upgrade E2E, or package
metadata mismatch. The workflow never changes versions automatically.

### 16.3 Release candidate

The release candidate is built from the intended `1.0.0` commit and retained as a CI artifact. The
same source identity is used for fresh-install, upgrade, consumer, and platform verification before
tagging that commit as `v1.0.0`.

### 16.4 Release documentation

The release requires Korean and English release notes, fresh-install instructions, a
`0.9.84 -> 1.0.0` migration guide, language-option documentation, local-profile reference,
machine-output compatibility notes, the bare-command behavior change, deprecated surfaces, known
limitations, downgrade recovery, and the post-1.0 roadmap.

The essential user guidance is:

```text
The default language is Korean.
Use `sage --lang en --help` for English help.
For an existing project, run `sage upgrade --check` and then `sage upgrade --apply`.
```

## 17. Release Blockers

Release is blocked by any of the following:

### Functional

- Korean default regression.
- Korean leakage in required English surfaces.
- Language-dependent hook decisions.
- Broken command, exit-code, JSON, schema, or generated-artifact contracts.
- Fresh-install failure.
- `0.9.84 -> 1.0.0` upgrade or rollback failure.
- Local language leakage into shared artifacts.

### Quality

- Unwired tests.
- `ResourceWarning`.
- Catalog or placeholder mismatch.
- Stale semantic spec/runtime render relationship.
- Stale bilingual user documentation.
- Missing wheel or sdist resources.
- Unresolved P0 or P1 issues.

### Release process

- Version or tag mismatch.
- Missing migration or release documentation.
- Undocumented known issue or workaround.
- Missing clean-install evidence.
- Failed platform smoke.

P2 or lower known issues may be accepted only when they do not violate a 1.0 invariant and their
impact, workaround, and tracked follow-up are documented.

## 18. Workstream Exit Criteria

### 18.1 Cleanup complete

- Every test file is executed or explicitly excluded.
- The two current runner omissions are connected.
- All tests pass without `ResourceWarning`.
- Blocking static rules pass.
- Comments and internal docstrings follow the Korean-default policy; stale and dead comments are removed.
- Every deletion has recorded evidence.
- Public behavior and the Korean baseline remain equivalent.

### 18.2 SSOT migration complete

- Internal semantic SSOT is English.
- All 13 CORE skills have neutral specifications.
- All six CORE agents have normalized specifications.
- All seven hook specifications follow the required contract structure.
- Runtime renders track and conform to canonical sources.
- User documentation pairs and hashes are valid.
- Historical approval-bound documents are unchanged.

### 18.3 Localization complete

- Bare `sage`, Korean help, and English help follow the agreed contract.
- Every CLI and hook user message is localized.
- CORE skills follow selected conversation language.
- New cycles write Phase 00-06 prose in the language resolved at cycle creation.
- Phase 00, cycle state, context packets, and same-stem phase documents agree on one immutable
  `Document-Language`; conflict and legacy paths pass their specified gates.
- Korean and English catalogs have full parity.
- English surfaces contain no uncategorized Korean text.
- Machine output and decisions are locale-independent.
- Wheel and installed consumer assets include both locales.

### 18.4 Upgrade complete

- Supported fresh installs pass.
- Immutable `0.9.84` fixtures upgrade successfully.
- A second upgrade is a no-op.
- Failure injection proves rollback.
- User policy and user-owned assets remain unchanged.
- Parameterized and isolated candidate tests prove that version axes can converge on `1.0.0`.
- The repository's actual version values remain unchanged until the user authorizes release.

### 18.5 Release complete

- The user explicitly authorized the `1.0.0` release after reviewing implementation and Phase 05.
- Required CI and platform matrices pass.
- Candidate artifacts pass wheel, sdist, and pipx-style checks.
- Version sources and tag agree.
- Korean and English release/migration documentation is complete.
- No release blocker remains.

## 19. Implementation Order and Change Isolation

The implementation plan derived from this design must preserve the following order:

1. Baseline evidence and output inventory.
2. Test-runner repair and warning cleanup.
3. Behavior-preserving cleanup.
4. SSOT ownership/language migration.
5. Language context, Korean catalog parity, and top-level CLI.
6. Remaining CLI commands.
7. Hook decision/reason separation and hook catalogs.
8. CORE skill localization behavior.
9. Upgrade command and immutable migration fixtures.
10. Cross-platform, packaging, documentation, and publication hardening.

Changes must remain reviewable and bisectable. In particular:

- Do not mix comment translation with function restructuring.
- Do not mix runner replacement with product changes.
- Do not mix dead-code deletion with public API removal.
- Do not mix Korean parity migration with English wording changes.
- Do not mix locale changes with hook decision logic.
- Do not mix profile migration with unrelated template cleanup.
- Do not mix release version stamping with functional changes.

## 20. Final Definition of Done

SAGE is `READY_FOR_USER_RELEASE_DECISION` only when all implementation, cleanup, SSOT,
localization, upgrade-readiness, packaging, and independent-review criteria above pass while the
repository version remains unchanged.

SAGE `1.0.0` is complete only after the user then explicitly authorizes release and all of the
following are true:

- The executable test inventory is complete and warning-free.
- Cleanup has preserved all supported behavior.
- Internal semantic SSOT uses English, while project-owned comments and internal docstrings follow
  the Korean-default policy.
- Korean remains the default and English is fully supported for the agreed CLI, hook, and CORE
  skill and Phase 00-06 document surfaces.
- Locale selection cannot affect governance, machine output, shared materialization, or audits.
- Fresh installs and the supported `0.9.84` upgrade path are verified on real packaged artifacts.
- User-owned project state survives upgrade and failed upgrades roll back safely.
- Version, package, manifest, documentation, and tag release gates all pass.
- Korean and English release and migration documentation are complete.
- The post-1.0 items remain explicitly outside the release rather than delaying it through scope
  creep.
